# دستور کار تست بازسازی زیر بار سنگین

هدف: اطمینان از اینکه بازسازی اسناد، **در شلوغ‌ترین حالت سیستم**، داده‌ی درست تولید می‌کند.

> ⚠️ **روی دیتابیس اصلی اجرا نکنید.** اول یک کپی بگیرید. بازسازی، ردیف‌های سند را
> پاک و از نو می‌سازد و در صورت وجود شماره سند تکراری، عمداً بازنویسی می‌کند.

## گام ۲ — ایجاد شلوغ‌ترین حالت

هدف: بیشترین همزمانی ممکن. هر چهار مورد را **هم‌زمان** برقرار کنید:

### الف) همه‌ی بخش‌های بازسازی با هم

در پنجره‌ی اتوباز:
- **همه‌ی تیک‌ها** را بزنید (سند فروش، خرید، خزانه، انتقالی، خروج مواد، … تا C11)
- تیک **«پردازش موازی (Parallel)»** روشن
- تیک **«پردازش با حداقل ظرفیت»** خاموش
- «تعداد روزهایی که برگردد» را روی بازه‌ی کامل بگذارید

این باعث می‌شود یازده بخش هم‌زمان اجرا شوند — یعنی بیشترین فشار روی استخر اتصال
و بیشترین رقابت روی قفل ساخت شماره سند.

### ب) کاربران واقعی هم‌زمان

از **چند ایستگاه دیگر** (حداقل ۳ تا)، هم‌زمان با بازسازی این کارها را انجام دهید:
- ثبت و ذخیره‌ی فاکتور فروش جدید
- ثبت و ذخیره‌ی برگه خزانه‌داری جدید (این مسیر مستقیماً `GENSANADKHAZ` را صدا می‌زند)
- ویرایش و ذخیره‌ی مجدد یک فاکتور قدیمی
- گرفتن گزارش تراز آزمایشی **در حین اجرا** (تست پنجره‌ی سند نیمه‌کاره)

### ج) دو نسخه‌ی هم‌زمان اتوباز

اگر می‌خواهید سخت‌ترین حالت را بسازید، **دو نسخه‌ی اتوباز را هم‌زمان** روی
یک دیتابیس اجرا کنید. این تنها حالتی است که قفل درون‌پروسه‌ای «سند روزانه»
پوشش نمی‌دهد و ارزش دارد بدانید چه می‌شود.

### د) اجرای تکراری

«تعداد تکرار» را روی ۲ یا ۳ بگذارید تا بازسازی پشت سر هم اجرا شود.
اجرای دوم روی داده‌ای کار می‌کند که اجرای اول ساخته — تست خوبی برای
تکرارپذیر بودن (Idempotency).

## گام ۳ — نگاه به لاگ

فایل `C:\CORRECT\AUTO_BAZ_LOG\...txt` را باز کنید. دنبال این خطوط بگردید:

```
سند خزانه - تعداد رکورد: N | هدر جدید: M | موازی: True | MaxDegreeOfParallelism: X
پايان باز سازي سند های خزانه - N رکورد در T ثانیه با Y Thread همزمان

سند فروش - تعداد رکورد: N | موازی: True | MaxDegreeOfParallelism: X
پایان بازسازی سند فروش - N رکورد در T ثانیه با Y Thread همزمان
```

**چه چیزی را بررسی کنید:**

| نشانه | معنی |
|---|---|
| `Thread همزمان` نزدیک به ۱ | موازی‌سازی کار نمی‌کند — گلوگاهی باقی مانده |
| `Thread همزمان` نزدیک به `MaxDegreeOfParallelism` | موازی‌سازی سالم است |
| خط هشدار «شماره سند تکراری داشتند» | داده‌ی قبلی آسیب دیده بوده و ترمیم شد — عدد را یادداشت کنید |
| هر خط «خطا» | باید بررسی شود |

همچنین به دنبال خطای **«Timeout expired ... connection pool»** بگردید. اگر دیدید،
یعنی سقف اتصال کم است و باید درجه‌ی موازی‌سازی پایین بیاید.

## گام ۴ — عکس «بعد»

دوباره `VERIFY_AFTER_REBUILD.sql` را اجرا کنید و با خروجی گام ۱ مقایسه کنید.

### معیار قبولی

| بررسی | انتظار |
|---|---|
| ۱. تعادل سند | **صفر ردیف.** این مهم‌ترین است؛ اگر ردیف داشت، جدی است |
| ۲. شماره سند تکراری خزانه | صفر — و اگر قبلاً عدد داشت، حالا باید صفر شده باشد |
| ۳. سند روزانه تکراری | اگر `SNDKH = 1` است، باید صفر باشد |
| ۴. بایگانی تکراری | نباید نسبت به «قبل» بیشتر شده باشد |
| ۵. سند بی‌ردیف | صفر یا همان عدد قبل |
| ۶. لینک شکسته | صفر |
| ۷. شرح نامتناسب | **صفر** — این مستقیماً قاطی شدن متغیر بین Threadها را می‌سنجد |
| ۸. تعداد ردیف خزانه | صفر ردیف مشکل‌دار |
| ۹. آمار کلی | تعداد سربرگ نباید بی‌دلیل بالا رفته باشد |

**اگر عدد «سربرگ» به‌طور محسوس بالا رفته** ولی تعداد فاکتور ثابت مانده، یعنی
سند تکراری ساخته شده — بررسی ۳ را دقیق نگاه کنید.

## گام ۵ — مقایسه‌ی مالی (اختیاری ولی توصیه‌شده)

قوی‌ترین تست: قبل و بعد از بازسازی، **تراز آزمایشی** بگیرید. جمع کل بدهکار و
بستانکار هر حساب کل نباید عوض شود (مگر اینکه واقعاً داده‌ی معیوبی ترمیم شده باشد).

```sql
SELECT  HES_K,
        SUM(ISNULL(BED,0)) AS JamBed,
        SUM(ISNULL(BES,0)) AS JamBes
FROM    dbo.DEED_DTL
GROUP BY HES_K
ORDER BY HES_K;
```

خروجی قبل و بعد را در دو فایل ذخیره و با هم Diff کنید. هر تفاوتی باید
توضیح‌پذیر باشد.

## اگر چیزی خراب بود

۱. **کل خروجی راستی‌آزمایی** (قبل و بعد) را نگه دارید
۲. **فایل لاگ اتوباز** را نگه دارید
۳. از دیتابیس بک‌آپ بگیرید تا وضعیت خراب قابل بررسی بماند
۴. مشخص کنید کدام بخش (خزانه؟ فروش؟) و کدام بررسی رد شد

با این سه چیز می‌شود دقیقاً فهمید کجا شکست.
