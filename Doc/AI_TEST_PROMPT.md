# پرامپت تست کامل سیستم سابقه و ردیابی فعالیت کاربران

> این فایل یک **متن آماده** است تا به یک هوش مصنوعی که روی کامپیوتر شما
> دسترسی دارد (به کد، به برنامه، و به یک **کپی** از دیتابیس) بدهید.
> از خط زیر تا انتهای فایل را کپی کنید و به آن بدهید.

---

تو یک مهندس تست هستی. قرار است ماژول «سابقه و ردیابی فعالیت کاربران»
(Audit Trail) در نرم‌افزار MrCorrect را **کامل** تست کنی و گزارش بدهی.

## قواعدی که باید رعایت کنی

این‌ها مهم‌تر از خود تست‌اند:

1. **حدس نزن.** اگر چیزی را نمی‌دانی یا نتوانستی اجرا کنی، بنویس
   «نمی‌دانم» یا «نتوانستم اجرا کنم» و دلیلش را بگو.
2. **دروغ نگو.** اگر تستی را انجام ندادی، ننویس که انجام دادی. اگر نتیجه
   مبهم بود، بنویس مبهم بود.
3. **توهم نزن.** فقط چیزی را گزارش کن که واقعاً روی صفحه دیدی یا خروجی
   واقعی یک کوئری بود. خروجی واقعی را عیناً کپی کن.
4. **هر ادعا باید مدرک داشته باشد** — خروجی کوئری، پیام خطا، یا اسکرین‌شات.
5. اگر تستی **شکست خورد**، سعی نکن توجیهش کنی. فقط دقیق بنویس چه شد.

## ⚠️ هشدار ایمنی — قبل از هر کاری بخوان

- **روی دیتابیس عملیاتی کار نکن.** اول یک `BACKUP` بگیر و روی یک کپی
  (مثلاً `YAZDSEPAR1405_TEST`) کار کن. این تست شامل **حذف رکورد** و اجرای
  `SYS_AUDIT_PURGE` است.
- رویه‌ی `SYS_AUDIT_BACKFILL` روی جدولی با بیش از یک میلیون ردیف کار
  می‌کند و ممکن است طول بکشد. فقط وقتی اجرایش کن که به بخش ۷ رسیدی.
- اگر به هر دلیلی مطمئن نیستی روی کپی هستی، **متوقف شو و بپرس**.

# بخش ۰ — شناخت سیستم

قبل از تست، این فایل‌ها را بخوان تا بدانی چه چیزی را تست می‌کنی:

- `Doc/AUDIT_TRAIL.md` — شرح فنی کامل
- `Prg_Proccessy/AUDIT/` — موتور (۷ فایل)
- `Prg_UI/Wins/WinMenus/CONFIGS/WIN_AUDIT_TRAIL.xaml.cs` — فرم گزارش

**خلاصه‌ی معماری** تا زودتر راه بیفتی:

- فراخوانی از سمت UI فقط یک نوشتن در صف حافظه است (`Channel`). هیچ
  رفت‌وبرگشتی با دیتابیس روی نخ رابط کاربری انجام نمی‌شود.
- یک نخ پس‌زمینه‌ی واحد، دسته‌ای (تا ۴۰۰ رویداد یا ۷۵۰ میلی‌ثانیه) در
  `SYS_AUDIT_EVENT` می‌نویسد.
- تشخیص `INSERT`/`UPDATE`/`DELETE` از راه `DiagnosticSource` خودِ
  `Microsoft.Data.SqlClient` است، نه تریگر دیتابیس و نه قلاب دستی. پس
  **هر دستوری از هر مسیری** دیده می‌شود.
- داخل تراکنش، رویداد **فقط بعد از `Commit`** ثبت می‌شود. اگر `Rollback`
  شود یا تراکنش بدون commit بسته شود، هیچ چیز ثبت نمی‌شود.
- اگر دیتابیس قطع باشد، رویدادهای حساس روی
  `%LOCALAPPDATA%\MrCorrect\AuditSpill\` می‌نشینند و در اجرای بعدی منتقل
  می‌شوند.

# بخش ۲ — آیا ساختار دیتابیس ساخته شد؟

ساختار باید **خودکار** موقع لاگین ساخته شده باشد (از مسیر مایگریشن
`ScriptSqly`). هیچ کار دستی لازم نیست.

```sql
-- ۲.۱ هر ۵ شیء باید موجود باشند
SELECT name, type_desc FROM sys.objects
WHERE name IN ('SYS_AUDIT_SESSION','SYS_AUDIT_EVENT',
               'VW_SYS_AUDIT_TIMELINE','SYS_AUDIT_PURGE','SYS_AUDIT_BACKFILL')
ORDER BY name;

-- ۲.۲ عرض ستون‌ها باید درست باشد (ACTION=32 ، ENTITY=200 بایت یعنی ۱۰۰ نویسه)
SELECT name, TYPE_NAME(user_type_id) AS نوع, max_length
FROM sys.columns
WHERE object_id = OBJECT_ID(N'dbo.SYS_AUDIT_EVENT')
  AND name IN ('ACTION','ENTITY','ENTITY_KEY','TITLE','FORM_NAME')
ORDER BY name;

-- ۲.۳ ایندکس‌ها
SELECT name, type_desc, is_unique FROM sys.indexes
WHERE object_id = OBJECT_ID(N'dbo.SYS_AUDIT_EVENT') AND name IS NOT NULL;

-- ۲.۴ نباید هیچ رویه‌ای با پیشوند SP_ مانده باشد
SELECT name FROM sys.objects WHERE name LIKE 'SP[_]SYS[_]AUDIT[_]%';

-- ۲.۵ نشست شما باید ثبت شده باشد
SELECT TOP 5 SESSION_ID, USER_NAME, WIN_USER, MACHINE_NAME, CLIENT_IP,
             APP_VERSION, DB_NAME, STARTED_AT, ENDED_AT
FROM dbo.SYS_AUDIT_SESSION ORDER BY STARTED_AT DESC;
```

**مقادیر انتظاری:**

| بررسی | انتظار |
|---|---|
| ۲.۱ | هر ۵ شیء موجود |
| ۲.۲ | `ACTION` = `varchar(32)`، `ENTITY` = `nvarchar` با `max_length = 200` |
| ۲.۳ | حداقل ۵ ایندکس به‌علاوه PK |
| ۲.۴ | **صفر ردیف** |
| ۲.۵ | یک ردیف با نام کاربری، نام کامپیوتر و IP **واقعی و درست** شما |

**بنویس:** خروجی هر پنج کوئری را عیناً کپی کن و بگو کدام با انتظار نخواند.

# بخش ۳ — دسترسی فرم گزارش

فرم عمداً **fail-closed** است: تا دسترسی ندهی باز نمی‌شود.

### ۳.۱ تست منفی (اول این)

بدون دادن هیچ دسترسی‌ای، در برنامه `Ctrl+F` بزن و «سوابق» را تایپ کن و
فرم را باز کن.

**انتظار:** پیام «دسترسی مشاهده‌ی سوابق برای شما تعریف نشده است» و بسته
شدن فرم.

همچنین این تلاش باید **خودش ثبت شده باشد**:

```sql
SELECT TOP 5 AT_SERVER, USER_NAME, ACTION, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE ACTION = 'AUDIT_VIEWED' ORDER BY LOG_ID DESC;
```

**انتظار:** ردیفی با عنوان «تلاش برای مشاهده‌ی سوابق بدون دسترسی».

> اگر فرم **بدون** دسترسی باز شد، این یک **ایراد امنیتی جدی** است. حتماً
> گزارش کن.

### ۳.۲ دادن دسترسی

```sql
SELECT IDH, FORMNAME, CAPTION FROM dbo.TFORMS WHERE FORMNAME = N'AUDITTRAIL';

-- به‌جای 78 کد کاربر خودت را از SALA_DTL.IDD بگذار
INSERT INTO dbo.SAL_CHEK (USERCO, [OBJECT], RUN, SEE, INP, UPD, DEL)
SELECT 78, IDH, 1, 1, 0, 0, 0
FROM dbo.TFORMS WHERE FORMNAME = N'AUDITTRAIL';
```

**بنویس:** آیا ردیف `AUDITTRAIL` خودکار در `TFORMS` ساخته شده بود؟ (باید
بوده باشد — مایگریشن می‌سازدش.)

### ۳.۳ تست مثبت

برنامه را ببند و دوباره باز کن، بعد فرم را باز کن.

**انتظار:** فرم باز می‌شود و ردیف‌ها را نشان می‌دهد.

> ❗ **این مهم‌ترین لحظه‌ی کل تست است.** این فرم تا امروز **هرگز باز نشده**.
> با دقت نگاه کن: آیا خطای data binding هست؟ آیا ستونی خالی است؟ آیا تاریخ
> و ساعت درست نمایش داده می‌شوند؟ آیا متن فارسی درست است یا به‌هم‌ریخته؟
> **اسکرین‌شات بگیر.**

# بخش ۴ — سناریوی اصلی: چرخه‌ی عمر یک پیش‌فاکتور

این قلب تست است. یک پیش‌فاکتور واقعی بساز و همه‌ی کارها را رویش انجام بده.
بعد از هر مرحله **چند ثانیه صبر کن** (نوشتن دسته‌ای است، تا ۷۵۰ میلی‌ثانیه
تأخیر دارد) و بعد در فرم سوابق نگاه کن.

| # | کاری که می‌کنی | `ACTION` انتظاری | `CATEGORY` |
|---|---|---|---|
| ۱ | فرم پیش‌فاکتور را باز کن | `OPEN_FORM` | ۱ |
| ۲ | یک پیش‌فاکتور جدید ثبت کن | `INSERT` | ۲ |
| ۳ | مبلغ یا یک قلم کالا را ویرایش کن | `UPDATE` | ۲ |
| ۴ | یک خانه‌ی امضا را بزن | `SIGN` | ۳ |
| ۵ | همان امضا را بردار | `UNSIGN` | ۳ |
| ۶ | پیش‌نمایش چاپ بگیر | `PREVIEW` | ۴ |
| ۷ | واقعاً چاپ کن (یا PDF) | `PRINT` | ۴ |
| ۸ | خروجی Excel از یک لیست بگیر | `EXPORT` | ۴ |
| ۹ | پیش‌فاکتور را حذف کن | `DELETE` | ۲ |

بعد شماره‌ی سند را در فرم سوابق جستجو کن، یا:

```sql
SELECT AT_SERVER, USER_NAME, ACTION, TITLE, ENTITY, ENTITY_KEY,
       FORM_NAME, SEVERITY, DETAIL
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE ENTITY_KEY LIKE N'%NUMBER=<شماره سند>%'
ORDER BY LOG_ID;
```

**برای هر ۹ مورد بنویس:**
- آیا ثبت شد؟ (بله / خیر)
- آیا `TITLE` فارسی **درست و خوانا** است یا کدهای `\u06...` دیده می‌شود؟
- آیا `ENTITY_KEY` شماره‌ی سند **واقعی** را دارد؟
- آیا `FORM_NAME` نام فرم **درستی** است؟
- برای `UPDATE`: آیا `DETAIL` ستون‌های تغییرکرده و **مقدار جدیدشان** را دارد؟

> ❗ اگر حتی یکی از این ۹ مورد ثبت **نشد**، دقیقاً بنویس کدام و چه کردی.
> این مهم‌ترین یافته‌ی ممکن است.

### ۴.۱ نکته‌ی مهم درباره‌ی امضا

یک کلیک روی هر خانه‌ی امضا، دستوری می‌سازد که **همه‌ی** خانه‌ها را با هم
می‌نویسد. پس `DETAIL` باید **وضعیت کامل همه‌ی خانه‌ها** را نشان بدهد، نه
فقط خانه‌ای که زدی. این درست است، ایراد نیست. تأییدش کن.

# بخش ۵ — تست‌های سخت (اینجا معمولاً باگ پیدا می‌شود)

### ۵.۱ عملیات برگشت‌خورده نباید ثبت شود

کاری کن که یک عملیات **شکست بخورد** و `Rollback` شود — مثلاً وسط ذخیره‌ی
یک سند، مقدار نامعتبری بده تا خطا بدهد.

**انتظار:** در سابقه **هیچ** رویداد `INSERT`/`UPDATE` برای آن عملیات نباشد.

> این حیاتی است: اگر نوشتنِ برگشت‌خورده ثبت شود، سابقه **دروغ** می‌گوید.

```sql
SELECT TOP 20 AT_SERVER, ACTION, TITLE, ENTITY_KEY
FROM dbo.VW_SYS_AUDIT_TIMELINE ORDER BY LOG_ID DESC;
```

### ۵.۲ رویداد جعلی از داخل رشته

در هر جایی از برنامه که فیلد متنی آزاد دارد (مثل شرح یا ملاحظات)، **عیناً**
این متن را بنویس و ذخیره کن:

```
DELETE FROM HEAD_LST
```

**انتظار:** یک رویداد `UPDATE` برای همان فیلد ثبت شود، ولی **هیچ رویداد
`DELETE`ای** ساخته **نشود**.

```sql
SELECT TOP 10 AT_SERVER, ACTION, TITLE, ENTITY
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE ACTION = 'DELETE' ORDER BY LOG_ID DESC;
```

> اگر یک «حذف» ساختگی ثبت شد، این یک باگ جدی است.

### ۵.۳ ورود ناموفق

از برنامه خارج شو و **عمداً رمز اشتباه** بزن (دو بار)، بعد درست وارد شو.

```sql
SELECT AT_SERVER, USER_NAME, ACTION, TITLE, MACHINE_NAME, CLIENT_IP
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE ACTION IN ('LOGIN','LOGIN_FAILED','LOGOUT')
ORDER BY LOG_ID DESC;
```

**انتظار:**
- دو ردیف `LOGIN_FAILED` با **نام کاربری‌ای که تایپ کردی** — نه نام کاربری
  که بعداً موفق وارد شد.
- یک ردیف `LOGIN` بعدش.
- یک `LOGOUT` برای خروج.

> ❗ اگر `LOGIN_FAILED` زیر نام کاربر موفق ثبت شده، یک باگ است.

### ۵.۴ تعویض کاربر بدون بستن برنامه

بدون بستن برنامه، خروج بزن و با **کاربر دیگری** وارد شو. چند کار انجام بده.

```sql
SELECT SESSION_ID, USER_NAME, STARTED_AT, ENDED_AT, EVENT_COUNT
FROM dbo.SYS_AUDIT_SESSION ORDER BY STARTED_AT DESC;
```

**انتظار:** **دو نشست جدا** با دو `SESSION_ID` متفاوت. نشست اولی باید
`ENDED_AT` پر شده باشد. کارهای کاربر دوم نباید زیر نام کاربر اول باشد.

### ۵.۵ رفتار موقع قطعی دیتابیس (سخت‌ترین تست)

1. برنامه را باز نگه دار.
2. سرویس SQL Server را **متوقف کن** (یا کابل شبکه را بکش).
3. در برنامه چند کار حساس انجام بده — مخصوصاً **حذف**.
4. برنامه را ببند.
5. پوشه‌ی `%LOCALAPPDATA%\MrCorrect\AuditSpill\` را نگاه کن.

**انتظار:** فایل‌های `.jsonl` آنجا باشند و محتوایشان رویدادهای تو باشد.

6. SQL Server را دوباره راه بینداز.
7. برنامه را باز کن و **هیچ کاری نکن**، فقط چند ثانیه صبر کن.
8. دوباره پوشه را نگاه کن و سابقه را کوئری بزن.

**انتظار:** پوشه خالی شده و رویدادها در `SYS_AUDIT_EVENT` هستند.

**بنویس:** چند فایل بود؟ چند رویداد؟ همه منتقل شدند یا بعضی ماندند؟

> نکته‌ی شناخته‌شده: رویدادهای منتقل‌شده از دیسک **فقط** به
> `SYS_AUDIT_EVENT` می‌روند و به `AMALIAT`/`USER_AUDIT_LOG` نه. این عمدی
> است، باگ نیست. اگر دیدی، تأییدش کن نه گزارش به‌عنوان ایراد.

### ۵.۶ بستن ناگهانی برنامه

چند کار حساس بکن و **بلافاصله** (کمتر از یک ثانیه) برنامه را از Task
Manager ببند (End Task).

**انتظار:** رویدادها یا در دیتابیس باشند یا در پوشه‌ی spill — ولی **گم
نشده باشند**.

# بخش ۶ — کارایی و عدم تداخل

این‌ها قیدهای اصلی بودند. واقعاً بسنج، حدس نزن.

### ۶.۱ کندی محسوس

یک کار سنگین تکراری انجام بده — مثلاً ۲۰ بار پشت سر هم یک فرم را باز و
بسته کن، یا یک فاکتور با ۵۰ قلم کالا ثبت کن.

**بنویس:** آیا کندی حس کردی؟ اگر ممکن است، زمان را با کرنومتر بگیر و با
حالت قبل از این تغییر مقایسه کن.

### ۶.۲ مصرف حافظه

در Task Manager مصرف حافظه‌ی `MrCorrect.exe` را یادداشت کن، بعد نیم ساعت
کار عادی بکن و دوباره نگاه کن.

**انتظار:** رشد غیرعادی نباشد. صف کران‌دار است (۲۰٬۰۰۰ رویداد) پس حتی با
دیتابیس قطع نباید حافظه بی‌نهایت رشد کند.

### ۶.۳ آیا رویدادی گم شده؟

```sql
SELECT SESSION_ID, USER_NAME, EVENT_COUNT, DROPPED_COUNT
FROM dbo.SYS_AUDIT_SESSION ORDER BY STARTED_AT DESC;
```

**انتظار:** `DROPPED_COUNT` صفر باشد. اگر صفر نیست، یعنی صف پر شده — گزارش
کن با چه کاری این اتفاق افتاد.

### ۶.۴ سرعت خود فرم گزارش

وقتی چند هزار ردیف جمع شد، فرم را باز کن و «نمایش بیشتر» را چند بار بزن.

**انتظار:** صفحه‌های بعدی به همان سرعت صفحه‌ی اول باشند (صفحه‌بندی
کلید-محور است، نه `OFFSET`). اگر هر صفحه کندتر از قبلی شد، گزارش کن.

# بخش ۷ — جدول‌های قدیمی و انتقال

### ۷.۱ آیا جدول‌های قدیمی هنوز پر می‌شوند؟

```sql
SELECT TOP 10 * FROM dbo.AMALIAT ORDER BY ADATE DESC;
SELECT TOP 10 * FROM dbo.USER_AUDIT_LOG ORDER BY ActionDateTime DESC;
```

**انتظار:** کارهای امروز تو در هر دو دیده شوند.

### ۷.۲ انتقال سابقه‌ی قدیمی

> ⚠️ فقط روی کپی. ممکن است چند دقیقه طول بکشد.

اول تعداد فعلی را بگیر:

```sql
SELECT COUNT(*) AS قبل FROM dbo.SYS_AUDIT_EVENT;
SELECT COUNT(*) AS amaliat FROM dbo.AMALIAT;
SELECT COUNT(*) AS userlog FROM dbo.USER_AUDIT_LOG;
```

بعد اجرا کن و **زمان بگیر**:

```sql
EXEC dbo.SYS_AUDIT_BACKFILL;
```

بعد:

```sql
SELECT COUNT(*) AS بعد FROM dbo.SYS_AUDIT_EVENT;
```

**انتظار:** تعداد بعد ≈ قبل + `amaliat` + `userlog`.

### ۷.۳ اجرای دوباره نباید ردیف تکراری بسازد

**دوباره** همان رویه را اجرا کن:

```sql
EXEC dbo.SYS_AUDIT_BACKFILL;
SELECT COUNT(*) AS بعد_از_دوبار FROM dbo.SYS_AUDIT_EVENT;
```

**انتظار:** عدد **دقیقاً همان** عدد بخش ۷.۲ باشد.

> ❗ این تست مهم است. یک باگ در همین گارد وجود داشت که باعث می‌شد هر بار
> لاگین کل جدول از نو درج شود. اگر عدد بالا رفت، آن باگ برنگشته است؟
> حتماً گزارش کن.

# بخش ۸ — پاک‌سازی

```sql
-- اول ببین چه داری
SELECT CATEGORY, COUNT(*) AS تعداد FROM dbo.SYS_AUDIT_EVENT GROUP BY CATEGORY;

-- پاک‌سازی با مقادیر واقعی
EXEC dbo.SYS_AUDIT_PURGE @KeepDaysNavigation = 90,
                         @KeepDaysOther      = 1825,
                         @ChunkSize          = 5000;

-- بعدش
SELECT CATEGORY, COUNT(*) AS تعداد FROM dbo.SYS_AUDIT_EVENT GROUP BY CATEGORY;
```

**انتظار:**
- رویدادهای ناوبری (`CATEGORY = 1`) قدیمی‌تر از ۹۰ روز حذف شوند.
- رویدادهای **حذف و امضا** (دسته‌ی ۲ و ۳) که کمتر از ۵ سال دارند **بمانند**.
- رویدادهای **امروز** دست‌نخورده بمانند.
- جدول در حین اجرا قفل طولانی نشود (تکه‌تکه است).

# بخش ۹ — جاهایی که می‌دانیم پوشش ندارند

این‌ها **باگ نیستند**، محدودیت شناخته‌شده‌اند. فقط تأیید کن که واقعاً
همین‌طور است و چیز دیگری هم پوشش ندارد:

1. **`AUTO_BAZ` در حالت اجرای مستقل** هیچ موتور سابقه‌ای ندارد.
2. **`WIN_F_NEWYEAR`** (ساخت سال مالی، `BACKUP`/`RESTORE`/`CREATE DATABASE`)
   سابقه نمی‌خورد.
3. **مقدار «قبل» فیلدها ثبت نمی‌شود** — فقط مقدار جدید. برای مقدار قبل،
   جدول‌های `TR_*` سر جایشان هستند.

**سؤال مهم برای تو:** در حین تست، آیا **جای دیگری** پیدا کردی که کار مهمی
انجام می‌شود ولی در سابقه نمی‌آید؟ مثلاً فرمی که رکورد تغییر می‌دهد ولی
ردیفی نمی‌سازد؟ اگر بله، دقیقاً بنویس کدام فرم و چه کاری.

## ایرادهای پیداشده

برای هر ایراد:

- **چه شد** — دقیقاً چه دیدی
- **چطور تکرارش کنم** — گام به گام
- **چقدر جدی است** — به نظر خودت
- **مدرک** — خروجی کوئری، پیام خطا، یا اسکرین‌شات

## چیزهایی که نتوانستی تست کنی

صادقانه بنویس کدام بخش‌ها را انجام ندادی و چرا.

## نظر کلی

با توجه به آنچه **واقعاً دیدی** (نه آنچه حدس می‌زنی): آیا این ماژول آماده‌ی
استفاده‌ی واقعی است؟ اگر نه، چه چیزی باید اول درست شود؟

---

**یادآوری آخر:** اگر چیزی را نمی‌دانی، بنویس «نمی‌دانم». گزارش صادقانه‌ی
ناقص، از گزارش کامل ولی ساختگی هزار برابر ارزشمندتر است.
