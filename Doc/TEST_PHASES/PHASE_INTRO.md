# معارفه — این را اول از همه بده

> این برگه را **قبل از فاز ۰** به هوش مصنوعی بدهید تا بداند وارد چه کاری
> می‌شود و با فازهای تکه‌تکه گیج نشود.

---

سلام. قرار است یک کار تستی **هشت‌فازی** انجام بدهی. این پیام فقط معارفه
است — **هنوز هیچ کاری نکن**. فقط بخوان و بگو آماده‌ای.

## چه چیزی را تست می‌کنی

نرم‌افزار **MrCorrect** یک ERP حسابداری فارسی (WPF / .NET 8 / SQL Server)
است. به‌تازگی یک ماژول به آن اضافه شده به نام **«سابقه و ردیابی فعالیت
کاربران»** (Audit Trail).

کاری که این ماژول می‌کند: یک **خط زمانی واحد** از هر کاری که هر کاربر در
نرم‌افزار انجام می‌دهد — چه فرمی باز کرد، چه چیزی ثبت/ویرایش/حذف کرد،
امضا زد یا برداشت، چاپ گرفت، از سیستم خروجی گرفت، کِی وارد و خارج شد — با
نام کاربر، ساعت، IP و نام کامپیوتر.

هدفش این است که مدیر بتواند در یک صفحه ببیند «فلانی دیروز چه کرد؟» یا
«این پیش‌فاکتور چه سرگذشتی داشت؟».

## چرا هشت فاز؟

چون کل تست در یک پیام جا نمی‌شود و کیفیت کار افت می‌کند. پس:

| فاز | موضوع |
|---|---|
| ۰ | آماده‌سازی محیط و ساخت کپی دیتابیس |
| ۱ | چرخه‌ی عمر یک سند از راه رابط کاربری واقعی |
| ۲ | ورود، خروج و تعویض کاربر |
| ۳ | چاپ، پیش‌نمایش و خروجی داده |
| ۴ | تست‌های خصمانه — آیا سابقه می‌تواند دروغ بگوید؟ |
| ۵ | مقاومت — قطعی دیتابیس و کشته شدن پروسه |
| ۶ | کارایی، حافظه و عدم تداخل با کار کاربر |
| ۷ | جدول‌های قدیمی، پاک‌سازی و گزارش نهایی |

**هر فاز جداگانه به تو داده می‌شود.** وقتی گزارش یک فاز را دادی، فاز بعد
را می‌گیری. هر فاز مستقل نوشته شده، پس اگر چیزی از فاز قبل یادت نماند
اشکالی ندارد — فقط این سه عدد را در پایان هر فاز نگه دار و در گزارش
بیاور:

1. `MAX(LOG_ID)` در پایان فاز
2. نام دیتابیسی که به آن وصلی
3. هر تغییری که در کد دادی

## ⛔ چهار قانون که در تمام هشت فاز برقرارند

### ۱. فقط روی کپی دیتابیس

تست‌ها شامل **قطع کردن SQL Server**، **حذف رکورد**، **کشتن پروسه** و
اجرای رویه‌ی پاک‌سازی هستند. هرگز روی دیتابیس عملیاتی اجرا نکن. فاز ۰
ساخت کپی را قدم‌به‌قدم می‌گوید.

### ۲. کد منبع را عوض نکن

اگر مجبور شدی (مثلاً یک `#if DEBUG return;` مانع اجرای برنامه شد): فایل و
خط و متن دقیق را گزارش کن، و در پایان با `git checkout -- <file>` برش
گردان.

### ۳. ⭐ با دست کار کن، نه با کد

**مهم‌ترین قانون. دو دور تست قبلی دقیقاً به همین دلیل ناکام ماندند.**

در آن دو دور، به‌جای استفاده از رابط کاربری، یک برنامه‌ی تستی ساخته شد که
متدهای موتور را **مستقیم** صدا می‌زد. آن کار ثابت می‌کند «موتور درست ثبت
می‌کند» — که از قبل می‌دانیم و با ۲۰۳ تست خودکار اثبات شده.

چیزی که **نمی‌دانیم** و تو باید جوابش را بدهی این است:
**آیا خودِ فرم‌ها موتور را درست صدا می‌زنند؟**

| ❌ ممنوع | ✅ لازم |
|---|---|
| `Audit.LoginFailed("ali", ...)` | در فرم لاگین رمز غلط تایپ کن |
| `AuditService.AttachUser(2, "ALI")` | واقعاً خروج بزن و با کاربر دیگر وارد شو |
| `AuditService.ShutdownAsync(50)` | در Task Manager روی `End Task` بزن |
| `Audit.Export("Excel", ...)` | در فرم روی دکمه‌ی خروجی اکسل کلیک کن |
| `Audit.Print(...)` | واقعاً چاپ بگیر |

**ساختن هر فایل `.cs` تستی که `Prg_Proccessy.AUDIT` را صدا بزند ممنوع
است.** تنها ابزارهای مجاز: خودِ برنامه، SQL Server Management Studio،
Task Manager، PowerShell (برای توقف سرویس)، و File Explorer.

اگر جایی واقعاً نمی‌شود با دست تست کرد، **بنویس نمی‌شود** — ننویس تست شد.

### ۴. حدس نزن، دروغ نگو

- اگر چیزی را نمی‌دانی: بنویس «نمی‌دانم».
- اگر تستی را انجام ندادی: بنویس انجام ندادم و چرا.
- اگر نتیجه مبهم بود: بنویس مبهم بود.
- اگر تستی **شکست خورد**: توجیهش نکن، فقط دقیق بنویس چه شد.
- هر ادعا باید **خروجی واقعی** یا اسکرین‌شات کنارش باشد.

> **یک باگِ پیداشده، از ده تستِ سبزِ ساختگی ارزشمندتر است.**
> در گزارش‌های قبلی جمله‌هایی مثل «بدون کوچک‌ترین مغایرت» نوشته شده بود
> برای تستی که اصلاً اجرا نشده بود. این را تکرار نکن.

## دو نکته‌ی فنی که مدام لازمت می‌شود

**۱) نوشتن دسته‌ای است.** ثبت سابقه روی نخ رابط کاربری فقط یک نوشتن در
**صف حافظه** است؛ یک نخ پس‌زمینه هر **۷۵۰ میلی‌ثانیه** (یا هر ۴۰۰ رویداد)
دسته‌ای در دیتابیس می‌نویسد.

> **پس بعد از هر کار ۳ ثانیه صبر کن و بعد کوئری بزن.** اگر بلافاصله کوئری
> بزنی نتیجه‌ی غلط می‌گیری و فکر می‌کنی چیزی ثبت نشده.

**۲) تراکنش.** داخل تراکنش، رویداد **فقط بعد از `Commit`** ثبت می‌شود.
اگر `Rollback` شود، عمداً هیچ چیزی ثبت نمی‌شود.

## کوئری‌ای که در همه‌ی فازها لازم داری

```sql
SELECT LOG_ID, DATE_S, TIME_S, USER_NAME, ACTION, CATEGORY, SEVERITY,
       ENTITY, ENTITY_KEY, FORM_NAME, TITLE, DETAIL
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <عدد شروع فاز>
ORDER BY LOG_ID;
```

معنی ستون‌ها:

| ستون | یعنی |
|---|---|
| `ACTION` | نوع کار: `INSERT`، `UPDATE`، `DELETE`، `SIGN`، `PRINT`، `LOGIN`، … |
| `CATEGORY` | ۱=ناوبری ۲=داده ۳=عملیات کاری ۴=چاپ/خروجی ۵=ورود/خروج ۶=امنیتی |
| `SEVERITY` | ۱=عادی ۲=قابل‌توجه ۳=حساس |
| `ENTITY` | نام جدول یا موجودیت |
| `ENTITY_KEY` | کلید رکورد، مثل `NUMBER=1234;TAG=20` |
| `FORM_NAME` | فرمی که کاربر در آن بوده |
| `TITLE` | متن فارسی آماده برای خواندن انسان |
| `DETAIL` | JSON جزئیات (ستون‌های تغییرکرده و مقدار جدیدشان) |

## اگر جایی گیر کردی

- اگر برنامه بالا نیامد یا کرش کرد → همان‌جا متوقف شو و گزارش بده. ادامه‌ی
  فازها بی‌معنی است.
- اگر دسترسی مدیر ویندوز نداری (برای توقف سرویس SQL) → در فاز ۵ بنویس
  «نتوانستم» و رد شو.
- اگر فقط یک کامپیوتر داری → تست همزمانی چند کاربر در فاز ۶ را رد کن و
  بنویس چرا.

هیچ‌کدام از این‌ها عیب تو نیست. **پنهان کردنشان عیب است.**

## حالا

اگر این معارفه را خواندی و فهمیدی، بنویس **«آماده‌ام»** و بگو:

1. آیا به کد پروژه دسترسی داری؟ (مسیرش کجاست)
2. آیا می‌توانی برنامه را اجرا کنی؟
3. آیا به SQL Server دسترسی داری؟
4. آیا دسترسی مدیر ویندوز داری (برای توقف سرویس و Task Manager)؟

بعد **فاز ۰** به تو داده می‌شود.
