# فاز ۴ — تست‌های خصمانه: آیا سابقه می‌تواند دروغ بگوید؟

**فاز ۴ از ۸.**

تا اینجا سنجیدیم که سابقه چیزهای درست را **ثبت می‌کند**. این فاز برعکس
است: می‌سنجد که چیزهای **نادرست را ثبت نکند**.

در سابقه‌ای که مبنای بررسی کارمندان است، **رویداد دروغ از رویداد نبوده هم
بدتر است**.

# تست ۴.۱ — عملیات برگشت‌خورده نباید ثبت شود

**چرا مهم است:** اگر نوشتنی که `Rollback` خورده در سابقه بیاید، بازرس
می‌بیند «فلانی سند را ثبت کرد» در حالی که هیچ چیزی در دیتابیس ننشسته.

**سه راه برای شکست دادن یک عملیات — حداقل دو تا را امتحان کن:**

**راه الف — خطای اعتبارسنجی دیتابیس:**
در فرم سند، مقداری بده که خطای SQL بدهد — مثلاً متنی خیلی بلندتر از عرض
ستون در یک فیلد، یا کد حسابی که وجود ندارد.

**راه ب — قفل کردن جدول از بیرون:**
از SSMS در یک پنجره‌ی جدا:
```sql
BEGIN TRAN;
SELECT 1 FROM dbo.HEAD_LST WITH (TABLOCKX, HOLDLOCK);
-- همین‌جا نگهش دار
```
حالا در برنامه سعی کن سندی ذخیره کنی → تایم‌اوت می‌خورد.
بعد در SSMS: `ROLLBACK;`

**راه ج — قطع وسط کار:**
وسط ذخیره‌ی یک سند سنگین، اتصال شبکه را قطع کن.

بعد از هر تلاش، ۵ ثانیه صبر کن:

```sql
SELECT LOG_ID, ACTION, ENTITY, ENTITY_KEY, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <شروع_فاز۴> ORDER BY LOG_ID;
```

**و مهم‌تر — تأیید کن که واقعاً در دیتابیس ننشسته:**

```sql
SELECT COUNT(*) FROM dbo.HEAD_LST WHERE NUMBER = <شماره سندی که سعی کردی>;
```

| نتیجه | معنی |
|---|---|
| در دیتابیس نیست **و** در سابقه هم نیست | ✅ پاس |
| در دیتابیس نیست ولی در سابقه **هست** | ❌ **باگ جدی** — سابقه دروغ می‌گوید |
| در دیتابیس هست و در سابقه هم هست | عملیات شکست نخورده؛ دوباره امتحان کن |

# تست ۴.۲ — رویداد جعلی از داخل متن

**چرا مهم است:** تشخیص نوشتن‌ها با خواندن متن SQL انجام می‌شود. اگر
محتوای رشته‌ها ماسک نشود، یک `SELECT` بی‌ضرر که کلمه‌ی `DELETE` در داده‌اش
دارد، یک «حذف فاکتور» **ساختگی** ثبت می‌کند.

**با دست، در فیلدهای متنی آزاد** (شرح، ملاحظات، توضیحات) این چهار متن را
در چهار رکورد مختلف بنویس و **ذخیره کن**:

```
DELETE FROM HEAD_LST
```
```
/* UPDATE DEED_HED SET N_S=1 */ -- TRUNCATE TABLE INVO_LST
```
```
سند باطل شد؛ DELETE FROM DEED_DTL انجام نشود
```
```
O'Brien -- DROP TABLE STUF_DEF
```

> متن چهارم عمداً یک `'` تکی دارد تا ماسک کردن نقل‌قول را هم بسنجد.

۳ ثانیه صبر کن:

```sql
SELECT LOG_ID, ACTION, ENTITY, ENTITY_KEY, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <شروع_فاز۴> ORDER BY LOG_ID;
```

**انتظار:** فقط `INSERT` یا `UPDATE` برای همان رکوردها. **هیچ**
`DELETE`، `TRUNCATE` یا `DROP` نباید ساخته شده باشد.

❌ اگر رویداد `DELETE` روی `HEAD_LST` یا `DEED_DTL` دیدی، **باگ جدی**.

**و بررسی کن متن سالم ذخیره شده:**

```sql
SELECT NUMBER, TAH, MOLAH FROM dbo.HEAD_LST WHERE NUMBER = <شماره سند>;
```

متن باید **عیناً** همان چیزی باشد که تایپ کردی — اگر بریده یا خراب شده،
بنویس.

# تست ۴.۳ — عملیات گروهی بزرگ

**چرا مهم است:** در هر تراکنش حداکثر ۵۰۰ دستور نگه داشته می‌شود تا حافظه
نترکد. اگر بیشتر شد، **خودِ ناقص بودن باید یک رویداد بشود** — نه اینکه
بی‌صدا گم شود.

**با دست:** یک عملیات گروهی سنگین انجام بده — مثلاً یک فاکتور با
**بیش از ۵۰۰ قلم کالا** ثبت کن، یا یک عملیات دسته‌ای که روی صدها رکورد
می‌نویسد (بستن حساب، محاسبه‌ی پورسانت گروهی، و…).

```sql
SELECT LOG_ID, AT_SERVER, ACTION, SEVERITY, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <شروع_فاز۴> AND TITLE LIKE N'عملیات گروهی%'
ORDER BY LOG_ID DESC;
```

**انتظار (اگر از سقف رد شد):** رویدادی با عنوانی شبیه:

```
عملیات گروهی: ۶۲۰ تغییر در یک تراکنش — جزئیات ۱۲۰ مورد به‌دلیل سقف ثبت نشد
```

با `SEVERITY = 3`.

اگر عملیات گروهی به این بزرگی نداشتی یا نتوانستی بسازی، **بنویس نتوانستم**
و رد شو — حدس نزن.

# تست ۴.۴ — رمز عبور نباید در سابقه بیفتد

**چرا مهم است:** اگر مقدار فیلدهای تغییرکرده ثبت می‌شود، رمز عبور هم
ممکن است در `DETAIL` بیفتد.

**با دست:** رمز عبور یک کاربر را عوض کن (از فرم تعریف کاربران).

```sql
SELECT LOG_ID, ACTION, ENTITY, TITLE, DETAIL
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <شروع_فاز۴> ORDER BY LOG_ID DESC;
```

**انتظار:** رویداد ثبت شود، ولی `DETAIL` نباید رمز را به‌صورت خوانا داشته
باشد — باید ماسک شده یا اصلاً نیامده باشد.

❌ اگر رمز (حتی رمزنگاری‌شده) در `DETAIL` دیدی، **حتماً گزارش کن**.

همین را برای هر فیلد حساس دیگری که می‌شناسی تکرار کن.
