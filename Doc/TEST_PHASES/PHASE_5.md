# فاز ۵ — مقاومت: قطعی دیتابیس و کشته شدن پروسه

**فاز ۵ از ۸.**

این فاز کل ادعای «رویداد حساس گم نمی‌شود» را می‌سنجد. سخت‌ترین فاز است و
نیاز به دسترسی مدیر ویندوز دارد (توقف سرویس SQL Server).

---

## ⛔ یادآوری

1. فقط روی `YAZDSEPAR1405_TEST`. تأیید: `SELECT DB_NAME();`
2. کد را عوض نکن.
3. ⭐ **`ShutdownAsync` را مستقیم صدا نزن.** در دور قبل همین اشتباه شد و
   تست ۶ عملاً برعکس چیزی را سنجید که باید. `End Task` واقعی لازم است.
4. حدس نزن، دروغ نگو.

```sql
SELECT MAX(LOG_ID) AS شروع_فاز۵ FROM dbo.SYS_AUDIT_EVENT;
```

**پوشه‌ای که مدام نگاهش می‌کنی:**
```
%LOCALAPPDATA%\MrCorrect\AuditSpill\
```

# تست ۵.۱ — قطعی کامل دیتابیس

**گام به گام:**

1. برنامه را باز نگه دار و وارد شده باش.
2. پوشه‌ی spill را **کاملاً خالی کن**.
3. `MAX(LOG_ID)` را یادداشت کن.
4. **سرویس SQL Server را متوقف کن** (PowerShell با دسترسی مدیر):
   ```powershell
   Stop-Service 'MSSQL$SQL2022'
   ```
   (اگر نام سرویس فرق دارد: `Get-Service *SQL*`)
5. حالا در برنامه **۵ کار حساس** انجام بده — ترجیحاً **حذف** و **امضا**.
   برنامه احتمالاً خطای اتصال می‌دهد؛ طبیعی است، کارت را بکن.
6. پوشه‌ی spill را نگاه کن.

**انتظار:** فایل‌های `.jsonl` آنجا باشند.

**یکی را با Notepad باز کن و چند خط اولش را در گزارش بیاور.** باید JSON
باشد با نام کاربر، عنوان فارسی و شناسه‌ی نشست.

7. برنامه را **عادی ببند**.
8. **سرویس را راه بینداز:**
   ```powershell
   Start-Service 'MSSQL$SQL2022'
   ```
9. برنامه را باز کن و **هیچ کاری نکن** — فقط ۱۵ ثانیه صبر کن.

> ⭐ این مرحله عمدی است. انتقال باید **بدون** اینکه کاربر کار تازه‌ای بکند
> انجام شود. اگر فقط با ترافیک جدید منتقل شود، یک باگ است (و قبلاً بوده).

10. دوباره نگاه کن:

```sql
SELECT LOG_ID, AT_SERVER, USER_NAME, ACTION, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <شروع_فاز۵> ORDER BY LOG_ID;
```

**در گزارش بنویس:**

| | عدد |
|---|---|
| چند کار حساس انجام دادی | |
| چند فایل در spill ساخته شد | |
| چند خط داخل فایل‌ها بود | |
| چند رویداد به دیتابیس منتقل شد | |
| پوشه خالی شد؟ | |

❌ اگر عددها نخواندند، **دقیقاً بنویس چند تا گم شد**.

> ⚠️ یک نکته‌ی شناخته‌شده که **باگ نیست**: رویدادهای منتقل‌شده از دیسک فقط
> به `SYS_AUDIT_EVENT` می‌روند و به `AMALIAT`/`USER_AUDIT_LOG` نه. این عمدی
> است. اگر دیدی، تأییدش کن، به‌عنوان ایراد گزارش نکن.

# تست ۵.۲ — کشته شدن واقعی پروسه (End Task)

**چرا مهم است:** این تنها حالتی است که ممکن است رویداد واقعاً گم شود، و
تا امروز **هرگز آزموده نشده**.

رویداد حساس در حالت عادی اول به صف حافظه می‌رود و تا ۷۵۰ میلی‌ثانیه آنجا
می‌ماند. اگر پروسه در آن پنجره **کشته** شود، هیچ کدی اجرا نمی‌شود.

**گام به گام:**

1. Task Manager را باز کن و آماده نگه دار (روی `MrCorrect.exe`).
2. `MAX(LOG_ID)` را یادداشت کن.
3. در برنامه **۵ کار حساس پشت سر هم** انجام بده (۵ حذف).
4. **بلافاصله** — کمتر از یک ثانیه — در Task Manager روی `End Task` بزن.
5. ۱۰ ثانیه صبر کن، بعد هر دو جا را بشمار:

```sql
SELECT COUNT(*) AS در_دیتابیس FROM dbo.SYS_AUDIT_EVENT WHERE LOG_ID > <عدد قبلی>;
```

و تعداد خطوط فایل‌های داخل پوشه‌ی spill.

**در گزارش بنویس:**

```
کارهای انجام‌شده       : ۵
در دیتابیس            : ؟
روی دیسک              : ؟
مجموع حفظ‌شده          : ؟
گم‌شده                : ؟
```

**این تست معیار قبول/رد قاطع ندارد** — هدفش اندازه‌گیری است، نه پاس شدن.
هر عددی درآمد، صادقانه بنویس. اگر همه حفظ شدند عالی؛ اگر چند تا گم شدند،
دقیقاً بگو چند تا و چه بودند.

6. این تست را **سه بار** تکرار کن و هر سه بار را جدا گزارش کن. این حالت
   ذاتاً غیرقطعی است و یک بار اجرا چیزی ثابت نمی‌کند.

# تست ۵.۳ — دیتابیس کند (نه قطع)

**چرا مهم است:** حالت خطرناک‌تر از «قطع» این است که دیتابیس **معلق** باشد
— اتصال باز است ولی جواب نمی‌دهد. آن‌وقت نخ پس‌زمینه گیر می‌کند.

**اگر می‌توانی** این را بساز: جدول `SYS_AUDIT_EVENT` را از SSMS قفل کن:

```sql
BEGIN TRAN;
SELECT 1 FROM dbo.SYS_AUDIT_EVENT WITH (TABLOCKX, HOLDLOCK);
-- نگهش دار
```

حالا در برنامه ۵ کار حساس بکن، بعد برنامه را **عادی ببند**.

بعد در SSMS `ROLLBACK;` بزن و برنامه را باز کن و ۱۵ ثانیه صبر کن.

**انتظار:** آن ۵ رویداد یا از spill منتقل شوند یا از قبل نوشته شده باشند —
گم نشوند.

اگر نتوانستی این وضعیت را بسازی، بنویس «نتوانستم» و رد شو.

# تست ۵.۴ — سلامت پس از همه‌ی این‌ها

```sql
SELECT SESSION_ID, USER_NAME, STARTED_AT, ENDED_AT, EVENT_COUNT, DROPPED_COUNT
FROM dbo.SYS_AUDIT_SESSION ORDER BY STARTED_AT DESC;
```

**بررسی کن:**
- آیا `DROPPED_COUNT` جایی صفر نیست؟ اگر نه، بنویس در کدام نشست و چقدر.
- آیا نشست‌هایی هستند که `ENDED_AT` ندارند؟ (آن‌هایی که پروسه‌شان کشته شد
  طبیعتاً ندارند — طبیعی است.)
- فرم سوابق را باز کن: آیا هنوز درست کار می‌کند و هشدار «رویداد گم شده»
  نشان می‌دهد یا نه؟
