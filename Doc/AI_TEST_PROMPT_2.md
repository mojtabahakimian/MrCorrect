# پرامپت تست — دور دوم (بخش‌های سختِ انجام‌نشده)

> دور اول فقط بخش‌های ۱ تا ۴ اجرا شد. این پرامپت **فقط** بخش‌هایی را پوشش
> می‌دهد که انجام نشدند — و همان‌ها ارزشمندترین‌اند.
> از خط زیر تا انتهای فایل را کپی کنید و به هوش مصنوعی بدهید.

---

تو یک مهندس تست هستی. قرار است بخش‌های **سختِ** ماژول «سابقه و ردیابی
فعالیت کاربران» (Audit Trail) در نرم‌افزار MrCorrect را تست کنی.

یک دور تست قبلاً انجام شده و بخش‌های پایه (بیلد، ساخت ساختار، باز شدن فرم
گزارش، چرخه‌ی عمر سند) **پاس شده‌اند**. آن‌ها را دوباره تست نکن. کار تو
دقیقاً همان چیزهایی است که دور قبل انجام **نشد**.

---

# ⛔ چهار قانون — این‌ها مهم‌تر از خود تست‌اند

دور قبل هر چهار مورد نقض شد. اگر دوباره نقض شوند، گزارش بی‌ارزش است.

### ۱. روی دیتابیس عملیاتی کار نکن

دور قبل مستقیم روی `YAZDSEPAR1405` اجرا شد، در حالی که گزارش ادعا کرد
«دیتابیس عملیاتی دست‌نخورده باقی ماند». هر دو نمی‌توانند درست باشند.

این تست شامل **قطع کردن SQL Server**، **حذف رکورد**، و اجرای
`SYS_AUDIT_PURGE` است. حتماً روی یک کپی کار کن:

```sql
BACKUP DATABASE YAZDSEPAR1405 TO DISK = 'C:\temp\yz.bak' WITH INIT;
RESTORE DATABASE YAZDSEPAR1405_TEST FROM DISK = 'C:\temp\yz.bak'
WITH MOVE 'YAZDSEPAR1405'     TO 'C:\temp\yz_test.mdf',
     MOVE 'YAZDSEPAR1405_log' TO 'C:\temp\yz_test_log.ldf', REPLACE;
```

**قبل از شروع هر تست، این را اجرا کن و خروجی‌اش را در گزارش بیاور:**

```sql
SELECT DB_NAME() AS [دیتابیسی که واقعاً به آن وصلم];
```

اگر خروجی `YAZDSEPAR1405_TEST` نبود، **متوقف شو**. رشته‌ی اتصال برنامه را
هم به همان کپی تغییر بده و تأیید کن که برنامه به کپی وصل است.

### ۲. کد منبع را عوض نکن

دور قبل `USER_LOGIN.xaml.cs`، `AuditSchema.cs` و `TestRunner` تغییر داده
شدند. این تست دیگر لازمش ندارد.

اگر **مجبور** شدی چیزی را برای اجرا شدن برنامه عوض کنی (مثلاً یک
`#if DEBUG return;`):

- در گزارش، فایل و خط و متن دقیق تغییر را بنویس.
- بعد از تست حتماً برگردانش: `git checkout -- <file>`.
- در پایان `git status` بزن و خروجی‌اش را در گزارش بیاور تا معلوم باشد
  چیزی جا نمانده.

### ۳. چیزی را که تست نکردی ادعا نکن

دور قبل جمع‌بندی نوشت «ثبت ورودهای ناموفق … بدون کوچک‌ترین مغایرت» در
حالی که هیچ خروجی‌ای برای آن نشان نداده بود.

هر ادعا باید **خروجی واقعی** کنارش باشد. اگر تستی را انجام ندادی، در
بخش «انجام‌نشده‌ها» بنویسش. این عیب نیست؛ پنهان کردنش عیب است.

### ۴. حدس نزن، دروغ نگو

اگر چیزی را نمی‌دانی یا نتیجه مبهم بود، بنویس «نمی‌دانم» یا «مبهم بود».
اگر تستی **شکست خورد**، توجیهش نکن — فقط دقیق بنویس چه شد. یک باگِ
پیداشده از ده تستِ سبزِ ساختگی ارزشمندتر است.

# آنچه باید بدانی

- ثبت سابقه روی نخ رابط کاربری فقط یک نوشتن در **صف حافظه** است. یک نخ
  پس‌زمینه هر **۷۵۰ میلی‌ثانیه** (یا هر ۴۰۰ رویداد) دسته‌ای می‌نویسد.
  **پس بعد از هر کار، ۲ تا ۳ ثانیه صبر کن و بعد کوئری بزن.**
- داخل تراکنش، رویداد **فقط بعد از `Commit`** ثبت می‌شود.
- اگر دیتابیس قطع باشد، رویدادهای **حساس** روی
  `%LOCALAPPDATA%\MrCorrect\AuditSpill\` می‌نشینند (فایل‌های `.jsonl`) و
  در اجرای بعدی منتقل می‌شوند.
- «حساس» یعنی: حذف، امضا، چاپ، خروجی، ورود و خروج.

کوئری‌ای که مدام لازمت می‌شود:

```sql
SELECT TOP 30 LOG_ID, AT_SERVER, USER_NAME, ACTION, CATEGORY, SEVERITY,
              ENTITY, ENTITY_KEY, FORM_NAME, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE ORDER BY LOG_ID DESC;
```

# تست ۱ — عملیات برگشت‌خورده نباید ثبت شود

**چرا مهم است:** اگر نوشتنی که `Rollback` خورده در سابقه بیاید، سابقه
**دروغ** می‌گوید. بازرس می‌بیند «فلانی سند را ویرایش کرد» در حالی که هیچ
تغییری در دیتابیس ننشسته.

**چطور:** کاری کن یک عملیات وسط کار **شکست بخورد**. چند راه:
- وسط ذخیره‌ی یک سند، مقداری بده که خطای دیتابیس بدهد (مثلاً متنی بلندتر
  از عرض ستون، یا کد حسابی که وجود ندارد).
- یا جدول هدف را از یک session دیگر با `BEGIN TRAN … TABLOCKX` قفل کن تا
  عملیات تایم‌اوت بخورد.

**قبل از شروع** بزرگ‌ترین `LOG_ID` را بگیر:

```sql
SELECT MAX(LOG_ID) AS قبل FROM dbo.SYS_AUDIT_EVENT;
```

عملیات را انجام بده تا شکست بخورد، ۳ ثانیه صبر کن، بعد:

```sql
SELECT LOG_ID, ACTION, ENTITY, ENTITY_KEY, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <قبل> ORDER BY LOG_ID;
```

| نتیجه | معنی |
|---|---|
| هیچ `INSERT`/`UPDATE`/`DELETE` برای آن سند نیست | ✅ پاس |
| رویداد داده‌ای برای سندی که ذخیره نشد ثبت شده | ❌ **باگ جدی** |

بعد تأیید کن که واقعاً در دیتابیس ننشسته:

```sql
SELECT COUNT(*) FROM dbo.HEAD_LST WHERE NUMBER = <شماره سند>;
```

---

# تست ۲ — رویداد جعلی از داخل رشته

**چرا مهم است:** تشخیص نوشتن‌ها با خواندن متن SQL انجام می‌شود. اگر
محتوای رشته‌های متنی ماسک نشود، یک `SELECT` بی‌ضرر که کلمه‌ی `DELETE` در
داده‌اش دارد، یک «حذف فاکتور» **ساختگی** ثبت می‌کند.

**چطور:** در هر فرمی که فیلد متنی آزاد دارد (شرح، ملاحظات، توضیحات)،
**عیناً** این متن را بنویس و ذخیره کن:

```
DELETE FROM HEAD_LST
```

بعد یک فیلد دیگر با این متن:

```
/* UPDATE DEED_HED SET N_S=1 */ -- TRUNCATE TABLE INVO_LST
```

۳ ثانیه صبر کن:

```sql
SELECT LOG_ID, ACTION, ENTITY, ENTITY_KEY, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <قبل> ORDER BY LOG_ID;
```

| نتیجه | معنی |
|---|---|
| فقط یک `UPDATE` برای همان فیلد، **هیچ** `DELETE` یا `TRUNCATE` | ✅ پاس |
| رویداد `DELETE` روی `HEAD_LST` ساخته شد | ❌ **باگ جدی** |

# تست ۳ — ورود ناموفق زیر نام چه کسی می‌نشیند؟

**چرا مهم است:** اگر تلاش ناموفق زیر نام کاربری ثبت شود که بعداً موفق وارد
شده، سابقه یک آدم بی‌گناه را متهم می‌کند.

**چطور:**
1. از برنامه خارج شو.
2. با نام کاربری **واقعی** ولی رمز اشتباه، دو بار تلاش کن.
3. با یک نام کاربری که **اصلاً وجود ندارد** (مثلاً `nobody_xyz`) یک بار.
4. حالا با کاربر درست وارد شو.
5. دوباره خارج شو.

```sql
SELECT LOG_ID, AT_SERVER, USER_NAME, ACTION, TITLE, IS_SUCCESS
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE ACTION IN ('LOGIN','LOGIN_FAILED','LOGOUT')
ORDER BY LOG_ID DESC;
```

**انتظار دقیق:**

| ردیف | `ACTION` | `USER_NAME` باید باشد |
|---|---|---|
| ۲ تلاش رمز غلط | `LOGIN_FAILED` | همان نام کاربری که تایپ کردی |
| تلاش با کاربر ناموجود | `LOGIN_FAILED` | `nobody_xyz` |
| ورود موفق | `LOGIN` | کاربر واقعی |
| خروج | `LOGOUT` | کاربر واقعی |

`TITLE` باید دلیل را هم بگوید («رمز عبور نادرست» یا «نام کاربری ناشناخته»).

❌ اگر `LOGIN_FAILED` زیر نام کاربرِ موفق ثبت شده، باگ است.

---

# تست ۴ — تعویض کاربر بدون بستن برنامه

**چرا مهم است:** اگر دو کاربر در یک نشست قاطی شوند، ردیابی بی‌معنی می‌شود.

**چطور:** **بدون بستن برنامه**، خروج بزن و با **کاربر دیگری** وارد شو.
با کاربر دوم چند کار قابل‌ثبت انجام بده (یک فرم باز کن، چیزی ویرایش کن).

```sql
SELECT SESSION_ID, USER_ID, USER_NAME, STARTED_AT, ENDED_AT,
       EVENT_COUNT, DROPPED_COUNT
FROM dbo.SYS_AUDIT_SESSION ORDER BY STARTED_AT DESC;
```

**انتظار:**
- **دو نشست جدا** با `SESSION_ID` متفاوت.
- نشست کاربر اول `ENDED_AT` پر شده باشد.
- `STARTED_AT` نشست دوم از لحظه‌ی ورود دوم باشد، نه از ابتدای اجرای برنامه.

بعد مطمئن شو کارهای کاربر دوم زیر نام کاربر اول نیست:

```sql
SELECT USER_NAME, COUNT(*) AS تعداد, MIN(LOG_ID) AS از_, MAX(LOG_ID) AS تا_
FROM dbo.VW_SYS_AUDIT_TIMELINE
WHERE LOG_ID > <قبل> GROUP BY USER_NAME;
```

# تست ۵ — قطعی دیتابیس (سخت‌ترین تست)

**چرا مهم است:** کل ادعای «رویداد حساس گم نمی‌شود» به همین بستگی دارد.

**گام به گام:**

1. برنامه را باز نگه دار و وارد شده باش.
2. پوشه را خالی کن تا نتیجه تمیز باشد:
   `%LOCALAPPDATA%\MrCorrect\AuditSpill\`
3. تعداد فعلی را بگیر: `SELECT MAX(LOG_ID) FROM dbo.SYS_AUDIT_EVENT;`
4. **سرویس SQL Server را متوقف کن:**
   ```
   net stop MSSQL$SQL2022
   ```
5. حالا در برنامه **۵ کار حساس** انجام بده — ترجیحاً **حذف** و **امضا**.
   (برنامه ممکن است خطای اتصال بدهد؛ طبیعی است. کارت را بکن.)
6. پوشه‌ی spill را نگاه کن.

**انتظار:** فایل‌های `.jsonl` آنجا باشند (`critical.jsonl` یا
`audit_<تاریخ>_<guid>.jsonl`). یکی را باز کن و محتوایش را در گزارش بیاور.

7. برنامه را ببند.
8. **SQL Server را راه بینداز:** `net start MSSQL$SQL2022`
9. برنامه را باز کن و **هیچ کاری نکن** — فقط ۱۰ ثانیه صبر کن.

> این مرحله عمدی است: انتقال باید **بدون** اینکه کاربر کار تازه‌ای بکند
> انجام شود. اگر فقط با ترافیک جدید منتقل شود، یک باگ است.

10. دوباره نگاه کن:

```sql
SELECT LOG_ID, AT_SERVER, USER_NAME, ACTION, TITLE
FROM dbo.VW_SYS_AUDIT_TIMELINE WHERE LOG_ID > <قبل> ORDER BY LOG_ID;
```

**در گزارش بنویس:** چند فایل بود؟ چند رویداد داخلشان؟ چند تا منتقل شد؟
آیا پوشه خالی شد؟ **اگر عددها نخواندند، دقیقاً بنویس چند تا گم شد.**

> ⚠️ یک نکته‌ی شناخته‌شده که **باگ نیست**: رویدادهای منتقل‌شده از دیسک
> فقط به `SYS_AUDIT_EVENT` می‌روند و به `AMALIAT`/`USER_AUDIT_LOG` نه.
> این عمدی است. اگر دیدی، تأییدش کن، به‌عنوان ایراد گزارش نکن.

# تست ۶ — بستن ناگهانی برنامه

۵ کار حساس بکن و **بلافاصله** (کمتر از یک ثانیه، قبل از ۷۵۰ میلی‌ثانیه‌ی
دسته‌بندی) برنامه را از Task Manager با **End Task** ببند.

**انتظار:** آن ۵ رویداد یا در دیتابیس باشند یا در پوشه‌ی spill — ولی
**گم نشده باشند**. هر دو جا را بشمار و مجموع را گزارش کن.

---

# تست ۷ — کارایی و حافظه

### ۷.۱ کندی واقعی

یک کار سنگین تکراری بکن: **۳۰ بار** پشت سر هم یک فرم را باز و بسته کن، یا
یک فاکتور با **۵۰ قلم کالا** ثبت کن. با کرنومتر زمان بگیر.

اگر می‌توانی، همین کار را با بیلدی از `master` (بدون ماژول سابقه) هم
بکن و دو عدد را کنار هم بگذار. اگر نمی‌توانی، بنویس «مقایسه‌ی پایه
نداشتم» و فقط زمان فعلی را بده.

### ۷.۲ حافظه

مصرف حافظه‌ی `MrCorrect.exe` را در Task Manager یادداشت کن، **نیم ساعت**
کار عادی بکن، دوباره نگاه کن. هر دو عدد را بنویس.

### ۷.۳ آیا رویدادی گم شده؟

```sql
SELECT SESSION_ID, USER_NAME, EVENT_COUNT, DROPPED_COUNT
FROM dbo.SYS_AUDIT_SESSION ORDER BY STARTED_AT DESC;
```

**انتظار:** `DROPPED_COUNT` صفر. اگر نیست، بنویس با چه کاری پر شد.

### ۷.۴ صفحه‌بندی عمیق

در فرم سوابق «نمایش بیشتر» را **۱۰ بار** بزن و زمان هر صفحه را حس کن.

**انتظار:** صفحه‌ی دهم به همان سرعت صفحه‌ی اول (صفحه‌بندی کلید-محور است،
نه `OFFSET`). ❌ اگر هر صفحه کندتر از قبلی شد، گزارش کن.

# تست ۸ — جدول‌های قدیمی و انتقال

### ۸.۱ هنوز پر می‌شوند؟

```sql
SELECT TOP 10 * FROM dbo.AMALIAT ORDER BY ADATE DESC;
SELECT TOP 10 * FROM dbo.USER_AUDIT_LOG ORDER BY ActionDateTime DESC;
```

**انتظار:** کارهای امروز تو در هر دو دیده شوند.

### ۸.۲ انتقال

> ⏱ روی جدولی با بیش از یک میلیون ردیف ممکن است چند دقیقه طول بکشد.
> **زمان بگیر.**

```sql
SELECT COUNT(*) AS قبل    FROM dbo.SYS_AUDIT_EVENT;
SELECT COUNT(*) AS amaliat FROM dbo.AMALIAT;
SELECT COUNT(*) AS userlog FROM dbo.USER_AUDIT_LOG;

EXEC dbo.SYS_AUDIT_BACKFILL;

SELECT COUNT(*) AS بعد FROM dbo.SYS_AUDIT_EVENT;
```

**انتظار:** `بعد` ≈ `قبل + amaliat + userlog`. اگر خیلی کمتر بود، یعنی
انتقال ناقص انجام شده — گزارش کن.

### ۸.۳ ⭐ اجرای دوباره نباید تکراری بسازد

**این مهم‌ترین تست این بخش است.**

```sql
EXEC dbo.SYS_AUDIT_BACKFILL;
SELECT COUNT(*) AS بعد_از_دوبار FROM dbo.SYS_AUDIT_EVENT;
```

**انتظار: عدد دقیقاً همان عدد ۸.۲ باشد.**

❌ اگر بالا رفت، یک باگ جدی برگشته: این رویه در هر لاگین اجرا می‌شود و
اگر گاردش کار نکند، **هر بار بالا آمدن برنامه کل جدول را از نو درج
می‌کند** و سابقه با ردیف تکراری باد می‌کند.

سومین بار هم اجرا کن و باز بشمار.

# تست ۹ — پاک‌سازی

```sql
SELECT CATEGORY, COUNT(*) AS تعداد FROM dbo.SYS_AUDIT_EVENT GROUP BY CATEGORY;

EXEC dbo.SYS_AUDIT_PURGE @KeepDaysNavigation = 90,
                         @KeepDaysOther      = 1825,
                         @ChunkSize          = 5000;

SELECT CATEGORY, COUNT(*) AS تعداد FROM dbo.SYS_AUDIT_EVENT GROUP BY CATEGORY;
```

**انتظار:**
- ناوبری (`CATEGORY = 1`) قدیمی‌تر از ۹۰ روز حذف شود.
- حذف و امضا (دسته‌ی ۲ و ۳) که کمتر از ۵ سال دارند **بمانند**.
- رویدادهای **امروز** دست‌نخورده بمانند.

مخصوصاً این را چک کن:

```sql
SELECT COUNT(*) AS حذف‌های_باقی‌مانده FROM dbo.SYS_AUDIT_EVENT
WHERE ACTION = 'DELETE';
```

❌ اگر رویداد حذفِ تازه پاک شده، باگ جدی است.

**حین اجرا** از یک session دیگر ببین جدول قفل طولانی می‌شود یا نه
(`sp_who2` یا `sys.dm_tran_locks`). باید تکه‌تکه باشد.

# تست ۱۰ — جاهایی که پوشش ندارند

این سه مورد **باگ نیستند**، محدودیت شناخته‌شده‌اند. فقط تأیید کن:

1. `AUTO_BAZ` در حالت اجرای مستقل هیچ موتور سابقه‌ای ندارد.
2. `WIN_F_NEWYEAR` (ساخت سال مالی، `BACKUP`/`RESTORE`/`CREATE DATABASE`)
   سابقه نمی‌خورد.
3. مقدار «قبل» فیلدها ثبت نمی‌شود — فقط مقدار جدید.

**و سؤال اصلی:** حین این تست‌ها، آیا جای **دیگری** دیدی که کار مهمی انجام
می‌شود ولی در سابقه نمی‌آید؟ فرمی که رکورد عوض می‌کند و ردیفی نمی‌سازد؟
اگر بله، دقیقاً بنویس کدام فرم و چه کاری.

## ایرادهای پیداشده

برای هر کدام: **چه شد** · **چطور تکرارش کنم** · **چقدر جدی است** ·
**مدرک** (خروجی کوئری یا اسکرین‌شات).

## تغییراتی که در کد دادم

فایل، خط، متن تغییر، و اینکه برگرداندمش یا نه. خروجی `git status` را
بیاور. اگر هیچ تغییری ندادی، بنویس «هیچ».

## آنچه تست نکردم

صادقانه فهرست کن و دلیل هر کدام را بگو.

## نظر نهایی

بر اساس آنچه **واقعاً دیدی**: آیا این ماژول آماده‌ی استفاده روی دیتابیس
عملیاتی است؟ اگر نه، چه چیزی اول باید درست شود؟

---

**یادآوری آخر:** گزارش صادقانه‌ی ناقص، از گزارش کاملِ ساختگی هزار برابر
ارزشمندتر است. اگر نصف تست‌ها را نتوانستی انجام بدهی، همان نصف را با مدرک
بده و بقیه را صادقانه بنویس انجام نشد.
