# بررسی به‌هم‌ریختن گزارش‌ها — چه چیزی را باید روی دیتابیس مشتری دید

این فایل نتیجه‌ی بررسی «چرا بعد از نسخه‌ی سابقه، گزارش‌ها مغایرت پیدا
کردند» است؛ به‌همراه کوئری‌هایی که خودِ مشتری/پشتیبان می‌تواند بزند تا
دقیقاً معلوم شود چه چیزی روی دیتابیس عوض شده.

---

## ۱) آنچه قطعی است (با مدرک، نه حدس)

**هیچ فایل DLL عوض نشده.** تنها کامیتی که در کل تاریخچه‌ی مخزن یک
`*.dll` را دست زده `3565921` است (ادغام PR #450) که خیلی پیش از کار
سابقه بوده. هیچ‌کدام از کامیت‌های سابقه حتی یک فایل DLL ندارند:

```
git log --all --name-only --diff-filter=AMD -- '*.dll'
git diff --name-only 8562cf8^ origin/master   # هیچ .dll و هیچ .mrt در خروجی نیست
```

**هیچ فایل `.mrt` عوض نشده.** آخرین تغییر `.mrt` هم پیش از کار سابقه بوده.

**`WINRPT.xaml.cs` الان دقیقاً همان حالت پیش از سابقه است** (کامیت
`af7b34c` کل قلاب‌های چاپ را برداشت):

```
git diff 8562cf8^ origin/master -- Prg_UI/Rpts/WINRPT.xaml.cs   # خروجی خالی
```

**کد فرم دفتر تفضیلی دست‌نخورده است.** آخرین تغییر
`F_MENU_KOL_MOIN_TAFZIL.xaml.cs` در `3565921` بوده، یعنی پیش از سابقه.

## ۲) چیزی که واقعاً عوض شده بود و ربطی به خودِ کد سابقه نداشت

در همان PR سابقه، دو چیز کنار هم عوض شد که اثرشان روی **دیتابیس** است،
نه روی کد گزارش:

1. ارجاع پروژه در `Prg_UI.csproj` از کلونِ کنارِ مخزن
   (`..\..\ScriptSqly` ⇒ `C:\prg\ScriptSqly`) به ساب‌ماژولِ داخل مخزن
   (`External\ScriptSqly`) عوض شد.
2. پینِ همان ساب‌ماژول از `37fa2ca` (۱۴۰۵/۰۵/۲۶) به `c858aa5` جلو رفت.

`ScriptSqly.Core` موتور مهاجرت دیتابیس است و `ScriptSqly.LetsGo(...)` در
**هر ورود کاربر** از `USER_LOGIN` صدا زده می‌شود. پس این دو تغییر با هم
یعنی: EXEی عملیاتی به‌جای ScriptSqlyِ خودِ توسعه‌دهنده، نسخه‌ای سه هفته
جلوتر را حمل می‌کرد و آن نسخه روی دیتابیس مشتری اجرا می‌شد.

اشیائی که در آن بازه اضافه/بازنویسی شده‌اند و **قبلاً در پینِ قدیمی
نبودند**:

| شیء | کِی اجرا می‌شود |
|---|---|
| `dbo.KALAS_PORSANT` (DROP + CREATE VIEW) | **هر ورود** |
| `dbo.VISITOR_PORSANT_ANBAR` (DROP + CREATE VIEW) | **هر ورود** |
| `dbo.SYS_AUDIT_*` (جدول/ویو/رویه‌ی سابقه) | **هر ورود** |
| `dbo.MOGHA_ANBAR` (بازنویسی، تای‌برک `id DESC`) | فقط اجرای دستیِ اسکریپت |
| `dbo.RecalcVisitorPorsant_ByDarsad` | فقط اجرای دستیِ اسکریپت |
| `dbo.CC_sp_*` (بستن بهای تمام‌شده) و `dbo.AI_*` | فقط با دکمه‌ی مربوطه |

نکته‌ی مهم: «اجرای دستیِ اسکریپت» یعنی دوبل‌کلیک روی شماره‌ی نسخه در فرم
ورود، یا دکمه‌ی اسکریپت در «درباره‌ی برنامه». بعد از هر به‌روزرسانی این
کار معمولاً انجام می‌شود — و در آن حالت **کلِ** بلوکِ مهاجرت‌های سه‌هفته‌ی
جلوتر روی دیتابیس مشتری اجرا شده است، از جمله بازنویسی `MOGHA_ANBAR` که
در خودِ اسکریپت «مرجع رسمی گزارش کارت انبار در کل سیستم» نامیده شده.

### اصلاحی که انجام شد

ارجاعِ `Prg_UI.csproj` شرطی شد: اگر `..\..\ScriptSqly` موجود باشد (روی
ماشین توسعه) **همان** استفاده می‌شود، دقیقاً مثل قبل؛ ساب‌ماژول فقط
جایگزینِ پشتیبان برای کلونِ تازه و CI است. یعنی بیلدِ عملیاتی دوباره
همان ScriptSqlyای را حمل می‌کند که خودِ توسعه‌دهنده کنترلش می‌کند و هیچ
مهاجرتِ منتشرنشده‌ای همراهِ نسخه نمی‌رود.

> این تغییر، تغییراتی را که **از قبل** روی دیتابیس مشتری نشسته برنمی‌گرداند.
> برای آن، بخش ۳ را ببینید.

## ۳) کوئری‌های تشخیصی روی دیتابیس مشتری

### ۳.۱ کدام اشیاء اخیراً بازنویسی شده‌اند؟

```sql
SELECT  o.type_desc, s.name AS [schema], o.name,
        o.create_date, o.modify_date
FROM    sys.objects o
JOIN    sys.schemas s ON s.schema_id = o.schema_id
WHERE   o.type IN ('V','P','FN','IF','TF')       -- ویو، رویه، تابع
  AND   o.modify_date >= DATEADD(DAY, -30, GETDATE())
ORDER BY o.modify_date DESC;
```

هر چیزی در این خروجی که **نامش با `SYS_AUDIT_` شروع نمی‌شود**، یک شیء
کاری است که در همین بازه بازنویسی شده. آن‌ها را با نسخه‌ی بکاپ مقایسه
کنید.

### ۳.۲ مقایسه‌ی متنِ یک شیء با بکاپ

روی دیتابیسِ فعلی و روی بکاپِ پیش از به‌روزرسانی، هر دو را بزنید و
خروجی را مقایسه کنید:

```sql
SELECT OBJECT_DEFINITION(OBJECT_ID(N'dbo.MOGHA_ANBAR'));
SELECT OBJECT_DEFINITION(OBJECT_ID(N'dbo.KALAS_PORSANT'));
SELECT OBJECT_DEFINITION(OBJECT_ID(N'dbo.QDAFTARTAFZIL2_H'));
SELECT OBJECT_DEFINITION(OBJECT_ID(N'dbo.Q_GARDESH_KHFR_DAFTAR_SUB'));
SELECT OBJECT_DEFINITION(OBJECT_ID(N'dbo.CUST_HESAB_DTL_EXTENDED'));
```

### ۳.۳ مشخصاً برای «مغایرت مانده‌ی دفتر تفضیلی»

گزارشِ چاپیِ F8 و لیستِ روی فرم، هر دو از همین تابع می‌خوانند. اگر عددِ
این کوئری با لیستِ روی فرم یکی باشد ولی با چاپ فرق کند، مشکل در
**جمعِ تجمعیِ داخل `.mrt`** است (ترتیب سطرها)، نه در داده:

```sql
-- @DT1/@DT2 تاریخ شمسی ۸ رقمی، @HESAB کد حساب تفضیلی
SELECT SUM(BED) AS SUM_BED, SUM(BES) AS SUM_BES,
       SUM(BED) - SUM(BES) AS MANDE
FROM   dbo.QDAFTARTAFZIL2_H(@DT1, @DT2, @HESAB);
```

اگر `MANDE` این کوئری با **هر دو** (لیست و چاپ) فرق داشت، داده‌ی زیرین
عوض شده و باید `OBJECT_DEFINITION` همین تابع با بکاپ مقایسه شود.

## ۴) آنچه نمی‌دانم

تا این لحظه **هیچ مسیری پیدا نکرده‌ام که خودِ کد سابقه عددِ مانده‌ی
گزارش دفتر تفضیلی را عوض کند.** کد سابقه نه SQLِ گزارش‌ها را دست می‌زند،
نه `.mrt` را، نه پارامترهای گزارش را، و `AuditCommandListener` فقط
`CommandText` و پارامترها را می‌خوانَد و هیچ چیزی را تغییر نمی‌دهد.

آنچه ثابت شده این است که **کدام نسخه از موتور مهاجرت داخل EXE می‌رفته**
عوض شده بود. اینکه دقیقاً کدام شیء روی دیتابیسِ آن مشتری بازنویسی شده،
فقط با کوئری‌های بخش ۳ روی همان دیتابیس معلوم می‌شود — از اینجا قابل
حدس زدن نیست و حدس نمی‌زنم.
